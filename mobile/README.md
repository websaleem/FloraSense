# FloraSense — Android app

An Expo / React Native client for the FloraSense API. Photograph a flower and it
returns the five closest species with confidence scores. The project layout,
release signing, and CodePipeline build mirror SecureBin.

```
mobile/
  app/           Screens (expo-router): camera, result, history, about
  components/    PredictionResult, HistoryItem
  constants/     config, theme
  hooks/         useCamera, useHistory
  services/      identifier (API), history (local storage), files
  types/         Shared types
  assets/        Launcher, adaptive, and splash icons
  playstore/     512px listing icon
  android/       Native project generated by `expo prebuild`
  buildspec.yml  CodeBuild build for the release AAB
```

## Running locally

```bash
cd mobile
npm install --legacy-peer-deps
cp .env.example .env          # point EXPO_PUBLIC_API_BASE_URL at dev or prod
npx expo run:android
```

`EXPO_PUBLIC_API_BASE_URL` must be the CloudFront domain
(`https://dev.florasense.websaleem.com`), never the Lambda Function URL — the
origin only accepts CloudFront-signed requests.

## How a photo is identified

1. The frame inside the on-screen reticle is cropped from the captured photo.
2. It is resized so the longest edge is 1024px and re-encoded as JPEG.
3. A `multipart/form-data` body is assembled **by hand**, and its SHA-256 goes in
   `x-amz-content-sha256`.
4. The API returns the top five predictions, which are stored in local history.

Step 3 is not optional. The API sits behind a CloudFront Origin Access Control
that SigV4-signs each origin request; CloudFront does not read the body, so it
signs whatever payload hash the client supplies, and Lambda function URLs reject
unsigned payloads. `FormData` picks its own boundary and never exposes the exact
bytes, so the hash could not be computed from it — which is why the body is built
manually, exactly as the website does.

## Privacy

Photos are sent only to identify a species and are deleted server-side before the
response returns. History (the photo and its predictions) stays on the device in
app-private storage, capped at the 50 most recent scans; evicted photos are
deleted with their record. The app requests only `CAMERA`, and the gallery option
uses the system photo picker, which needs no storage permission.

## Release builds

`buildspec.yml` builds the AAB in CodeBuild:

- The environment comes from the branch: `main` builds against
  `/florasense/mobile/prod/api-base-url`, any other branch against the dev
  parameter. A missing or non-https parameter fails the build rather than
  shipping a binary pointed at the wrong API.
- Signing material is read from SSM and passed to Gradle as
  `ORG_GRADLE_PROJECT_FLORASENSE_UPLOAD_*` environment variables rather than `-P`
  arguments, which would expose the passwords in the process list.
- `infra/mobile-ci-cd.yaml` provisions the pipeline. It is a V2 pipeline that
  triggers only on changes under `mobile/`, so backend, website, and training
  changes do not rebuild the app.

Before the first pipeline run, these must exist:

| SSM parameter | Type | Contents |
| --- | --- | --- |
| `/florasense/mobile/{dev,prod}/api-base-url` | String | CloudFront base URL |
| `/florasense/mobile/upload-keystore` | SecureString | base64 of `upload.jks` |
| `/florasense/mobile/upload-store-password` | SecureString | keystore password |
| `/florasense/mobile/upload-key-alias` | String | key alias |
| `/florasense/mobile/upload-key-password` | SecureString | key password |

Publishing to Google Play uses `android/fastlane` (`fastlane deploy track:alpha`)
with a Play service account JSON at `android/app/api.json`, which is gitignored.
